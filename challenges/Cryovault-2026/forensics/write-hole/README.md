## Challenge

> No prose was shipped with this one — just the handout.

**Provided files:** `bay0.img`, `bay1.img`, `bay2.img` (17 MiB each, `file` says `data`)

## TL;DR

Three RAID5 member disks with the md superblock scrubbed. Brute-force the geometry
(**32 KiB chunks, left-symmetric, bay order 1→2→0, 1 MiB data offset**) to get a clean
ext4 volume. A crash during a sealed-report update tore the stripe writes: three of six
AES-GCM records still hold the *previous* job's data. The sealing key was "burn after
read" — but the volume is mounted `data=journal`, so **four generations of the deleted
keyslot are still in the ext4 journal**. Rebuild the lost records as `parity XOR sibling`,
unseal with the key whose `key_id` matches the write-ahead intent file, and the three
custody-token shards concatenate to the flag.

## Recon

No superblock, no partition table, no strings worth reading:

```bash
file write-hole/*.img                 # -> data
ls -l write-hole/                     # 3 x 17825792 bytes
python3 -c "...find(bytes.fromhex('fc4e2ba9'))..."   # no mdadm magic anywhere
```

Three identically-sized members and no metadata means the geometry has to be inferred.
Two cheap measurements did most of the work:

**1. XOR all three members at the same offset.** For a 3-member RAID5 one chunk per
stripe is `D0 ^ D1`, so a consistent array XORs to zero *everywhere*, whichever disk
holds parity. Only 43 of 512 stripes were non-zero — this really is RAID5, and those 43
stripes are where the interesting damage lives:

| Stripes | Reading |
|---|---|
| 71–75 | the damage that matters (payload region) |
| 323, 341–347, 379 | free space the array never wrote (random fill) |
| 480–511 | the never-written tail |

**2. Entropy per 4 KiB block.** The first 1 MiB of every member is high-entropy noise and
the remaining 16 MiB is low-entropy structured data. That is the mdadm 1.2 **default
1 MiB data offset** with the superblock scrubbed. 2 data members × 16 MiB = 32 MiB, which
is exactly `8192 blocks × 4096` from the ext4 superblock found at `+0x100400`.

## Analysis

### Recovering the geometry

Chunk size, parity layout and disk order are 8 × 5 × 6 combinations. Checking for an ext4
magic is useless — the parity chunk is a byte-for-byte copy of chunk 0 whenever the third
chunk is zeroed, so **160 of the combinations "find" a valid superblock**. The honest
oracle is a full consistency check:

```python
for chunk in (4096, ..., 524288):
  for alg in ('left-asym','right-asym','left-sym','right-sym','raid4'):
    for perm in permutations(range(3)):
        assemble(); e2fsck -fn
```

Exactly one combination comes back clean:

```
e2fsck -fn array.img
ev-nas3: 31/512 files (3.2% non-contiguous), 1209/8192 blocks
```

→ **chunk 32 KiB, left-symmetric, array slots = (bay1, bay2, bay0), data offset 1 MiB.**

That the chunk size equals the 32 KiB sealed record size is not decoration: it makes every
record land on exactly one chunk, so a torn write can only ever lose whole records.

### What the volume says

```
/etc/nas.conf          opts=rw,noatime,data=journal ; raid5, write-intent bitmap: none (perf)
/stage/README.txt      keyslot delivered to /stage/.keyslot, BURN-AFTER-READ
/stage/isfc-stage.py   the sealing tool
/stage/job-0007.intent write-ahead SHA-256 of all 6 records + key_id b5125b19a47d9d61
/stage/payload.bin     196608 bytes = 6 x 32768
/stage/stage.log       job 7: "intent written, 6 records submitted (qd=6)" — no "fsync ok"
```

`stage.log` ends mid-job: jobs 5 and 6 both logged `6 records sealed, fsync ok`, job 7
never did. It also records `keyslot for job 7 was regenerated by operator (rotate)`, which
is why two different job-7 keys exist.

`isfc-stage.py` gives the sealing scheme: `AES-GCM`, `nonce = job||idx` (`>QI`),
`aad = b"payload.bin|<job>|<idx>"`, 32740 plaintext bytes per 32768-byte record, and the
intent file written and fsynced *before* the payload is touched.

### The torn write

Hashing each on-disk record against the intent, and reading back the plaintext nonce:

| rec | intent hash | nonce on disk | stripe | parity | data | mate |
|---|---|---|---|---|---|---|
| 0 | ✅ | job **7** | 72 | bay0 | bay2 | bay1 |
| 1 | ❌ | job **6** | 73 | bay2 | bay0 | bay1 |
| 2 | ✅ | job **7** | 73 | bay2 | bay1 | bay0 |
| 3 | ❌ | job **6** | 74 | bay1 | bay2 | bay0 |
| 4 | ✅ | job **7** | 74 | bay1 | bay0 | bay2 |
| 5 | ❌ | job **6** | 75 | bay0 | bay1 | bay2 |

Three of the six 32 KiB writes never reached their data member — those chunks still hold
job 6. This is the RAID5 write hole exactly: queue depth 6, power lost mid-flight, no
write-intent bitmap (`bitmap: none (perf)` in `nas.conf`), so nothing records which
stripes were in flight.

The parity, however, *was* updated. So for a lost chunk:

```
parity = new_data ^ new_mate        (parity landed)
new_mate                            (mate landed, hash verifies)
--------------------------------------------------
new_data = parity ^ new_mate        <- the lost record, recovered
```

Records 1 and 5 come back **bit-exact** this way: their rebuilt chunks match the intent
SHA-256 and the GCM tag verifies. Record 3 is the one the challenge keeps (see below).

### Getting the key back

The key is gone by design — `burn_after_read()` reads `/stage/.keyslot` and immediately
`os.unlink()`s it, so the key "lives only in RAM". Two things undo that:

1. `data=journal` journals **file data**, not just metadata, so the keyslot's contents went
   through the journal on every delivery.
2. The volume still has `needs_recovery` set — the journal was never replayed, so nothing
   has been checkpointed away.

```
debugfs -R "logdump -S" array.img   # 8 transactions, journal sequence 1..8
```

Parsing JBD2 by hand (descriptor tags → target fs blocks) yields one 64-byte keyslot per
transaction. The blobs are self-validating (`KSLT` magic, version, big-endian job number,
32-byte key, CRC32 of the first 48 bytes), so a plain `KSLT` scan plus a CRC check finds
them without touching the journal structures at all — and drops the one decoy hit in
`.thumbs-9.db`:

| journal seq | job | `key_id` | |
|---|---|---|---|
| 1 | 5 | `c44b43c950a294df` | consumed, logged |
| 3 | 6 | `772f2715dbe1362b` | consumed, logged |
| 5 | 7 | `9ec7c8a0d41d0324` | **pre-rotation, discarded** |
| 7 | 7 | `b5125b19a47d9d61` | ← matches the intent's `key_id` |

`key_id = sha256(key)[:16]` in the intent file is what picks the right job-7 slot:

```
f1d921fa87176e694601c89950e4bae1f38bae1e19b0e5ae5c4aa00b31fcfa3d
```

### Record 3: data without proof

Record 3's stripe (74) is the one place parity alone isn't enough. `parity ^ mate` produces
a chunk whose nonce is correctly `job 7 | idx 3` and whose 32740 plaintext bytes are *fully
coherent*: 439 lines, and every one matches the report grammar
`[YYYY-MM-DD HH:MM:SS] <verb> <noun> obj=EV-##### sha1=<16 hex> ok=[yn]` except the four
that should differ — the `part 4/6` header, the `PAD` tail, the trailing newline, and the
custody-token shard.

But it does **not** authenticate, and that is not just a lost tag:

- the GCM tag fails;
- recomputing the tag over the rebuilt ciphertext (GCM's tag is a function of the
  ciphertext and AAD, so this is the only tag that ciphertext can have) still does not
  reproduce the intent's SHA-256;
- the same re-seal pipeline reproduces the intent hash for **5/5** of the intact records,
  so the pipeline is right and the rebuilt *ciphertext body* differs from what was hashed.

**[Inference]** The most economical explanation is a generator artifact: the parity for
stripe 74 was built from a different draw of the part-4 report than the one hashed into the
intent. Both draws are coherent text, both carry the same injected shard line, so the
recovered plaintext is usable but can never be proven. Treated as unauthenticated, it is
corroborated three ways: the header says `part 4/6` of job 7, every log line conforms, and
its shard is 15 characters like the other two and opens the `isfar{` that shard 3/3 closes.

The flag is split across three records on purpose — one intact (`part 6/6`), one
parity-rebuilt and verified (`part 2/6`), one parity-rebuilt and unverifiable (`part 4/6`):

```
[custody-token] the custody token is split in 3 shards spread over this report;
                concatenate shard 1, 2, 3 in numeric order, no separators
```

## Exploitation

Full solve in [`solve.py`](solve.py) — pure Python plus `cryptography`, no `mdadm`, no loop
mount, no root. It reassembles the array, finds the intent file and payload by content,
repairs the torn records from parity, recovers the keyslot from the journal, unseals all
six records and prints the flag:

## Takeaways

- **XOR all members at the same offset before anything else.** It confirms RAID5 *and*
  maps the damage in one pass, because a consistent stripe XORs to zero regardless of
  which disk holds parity.
- **A magic-number check is not a geometry oracle.** 160 of 240 combinations produced a
  "valid" ext4 superblock, because parity duplicates chunk 0 whenever the third chunk is
  zeroed. `e2fsck -fn` picked the single right answer immediately — I should have gone
  there first instead of reasoning about which bay held the superblock.
- **Entropy maps find the data offset for free.** Scrubbed-superblock noise versus
  structured filesystem data showed the 1 MiB boundary without guessing at mdadm defaults.
- **"The key only lives in RAM" is false under `data=journal`.** Every delivered keyslot
  was still in an unreplayed journal. `needs_recovery` in the feature flags is the tell:
  nothing has been checkpointed away yet.
- **Self-validating blobs beat format parsing.** CRC-checking a 64-byte `KSLT` scan replaced
  a JBD2 descriptor-tag walk and rejected the decoy for free.
- **A GCM tag is a function of the ciphertext, not the plaintext.** Realising that killed
  an hour of trying to "repair the tag" on record 3: if the recomputed tag still doesn't
  reproduce the expected digest, the body is wrong and no tag will save it.
- Time lost: swapping the mate and victim bays in the stripe map. The reconstruction
  decrypted to pure noise and I briefly blamed the parity rather than my own role mapping.
  Print the full `parity/data/mate` assignment before trusting any rebuild.
